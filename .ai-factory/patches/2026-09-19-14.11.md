# Persistence imported world for physical-rules fingerprinting

**Date:** 2026-09-19 14:11
**Files:** src/simulation/models.py, src/simulation/contracts.py, src/simulation/__init__.py, src/persistence/sqlalchemy.py, tests/unit/test_reproducibility_contracts.py
**Severity:** high

## Problem

`$aif-verify` on M2.5 physical simulation failed architecture gates:
`persistence.sqlalchemy` imported `canonical_physical_rules_bytes` and
`physical_rules_fingerprint` from `world.models`, violating the modular-monolith
rule that persistence may only depend on simulation/infrastructure.

## Root Cause

Physical run-config persistence needed a stable fingerprint and canonical JSON
document for `PhysicalRules`. Those helpers lived only on `world.models`, and
the SQLAlchemy repository called them directly instead of going through the
simulation application boundary. The domain helpers were correct; the wrong
layer imported them.

## Solution

Added thin simulation facades `fingerprint_physical_rules` and
`canonical_physical_rules_document` that delegate to world helpers, with
`[FIX]` DEBUG logging. Persistence now imports those facades from
`simulation.models`. Exported the facades from `simulation.contracts` /
`simulation.__init__`. Added a unit test that the facade output matches the
world helpers so persistence can stay free of world imports.

## Prevention

- When persistence needs domain-derived digests or documents, add a simulation
  facade first; never import `world` under `src/persistence`.
- Keep architecture boundary tests in CI; they already catch `persistence -> world`.
- Prefer reviewing new codec/fingerprint helpers for which package owns the
  public import surface before wiring repositories.
