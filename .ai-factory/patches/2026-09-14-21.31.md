# Integration migrations could target the wrong database under dual URLs

**Date:** 2026-09-14 21:31
**Files:** src/infrastructure/settings.py, alembic/env.py, tests/integration/conftest.py, tests/unit/test_settings.py
**Severity:** high

## Problem

Integration Alembic upgrades called `load_migration_settings()`, which preferred
`PALIMPSEST_DATABASE_URL` whenever it was set. The integration fixture validated
`PALIMPSEST_TEST_DATABASE_URL` but did not bind Alembic to that DSN. When both
URLs were present (common with a local `.env` plus a test URL), migrations could
run against the non-disposable database instead of failing closed.

## Root Cause

Two independent URL resolution paths diverged:

1. The fixture loaded and validated the disposable test URL into `Settings`.
2. `command.upgrade()` re-resolved the target inside `alembic/env.py` from
   process settings, where runtime `DATABASE_URL` outranked `TEST_DATABASE_URL`.

The foundation rule “fail safely rather than migrating an ambiguous database”
was not enforced at either boundary.

## Solution

- `load_migration_settings` now fails with `SettingsError` when both URLs are
  present and disagree; agreeing URLs and test-only URLs still work.
- `alembic/env.py` prefers a programmatic `sqlalchemy.url` on the Alembic
  Config (never stored in `alembic.ini`).
- The integration fixture sets that Config URL to the validated test DSN and
  logs a recoverable WARNING when `DATABASE_URL` differs.
- Unit tests cover disagreeing and agreeing dual-URL cases.

## Prevention

- Any destructive DB fixture must pass the validated DSN into the tool that
  connects (Config option, explicit override), not rely on ambient env reload.
- When two URL settings can both be set, resolve with fail-closed equality
  checks before mutating schema.
- Review integration DB setup for “validate A, then connect using B” patterns.
