## Task 7: Implement immutable indexed filesystem publications

### Intent / Implementation Steps
1. Implement separate filesystem writer and reader classes against the Task 2 ports, rooted in an operator-configured directory. Use existing standard-library filesystem/JSON/hash support, not a new database or service.
2. Layout: `<root>/<sha256(run_id)>/<family>/<sha256(class,owner)>/snapshots/<boundary-as-16-hex>/<publication_id>/`. Store `manifest.json`, generated node descriptors, incoming/outgoing adjacency pages, node catalogue pages, and integrity index shards. No query-time recursive listing, sorting all publications, or scanning other runs.
3. A root manifest is at most 64 KiB. It lists up to 256 integrity-index shard digests, node-catalogue page digests/counts, scope/source/coverage metadata and graph digest. Select a shard by first two hex characters of node key; each shard maps generated descriptor/adjacency page keys to expected file digest and byte count and is at most 256 KiB. File names derive from node key, direction and numeric page only. A skew exceeding an index cap fails publication explicitly. Verify manifest→shard→page digests on reads, within query read/byte budgets.
4. Use one authoritative run commit point, not independently mutable per-scope heads. `<run-root>/state.json` is an atomic, at-most-4-KiB pointer/control record containing the last `committed_ref`, cumulative quota counters and at most one pending reservation. Immutable, at-most-64-KiB run commit manifests live at `commits/<digest>/manifest.json`; they reference bounded content-addressed scope-head indexes, exact-boundary indexes and immutable catalogue pages. Index records identify snapshot manifests by generated scope/B/publication tuples, never arbitrary paths. Exact B lookup first proves membership in the pinned committed boundary index; a stray directory or descriptor is not a published snapshot.
5. Under one exclusive writer lock per run, pre-encode and validate the bounded publication/index update plan. Persist/fsync an atomic reservation in `state.json` before writing staged payloads: expected publication identity, planned digests/counts, prior committed ref, and reserved publication slot/bytes. Quotas count cumulative encoded file bytes including graph, index, control, staging and retained orphan content, not filesystem block/journal overhead. Reserve the exact encoded new graph/index/catalogue file sizes plus a fixed 256 KiB conservative allowance for the reservation/commit/control records; reject before writing if this does not fit and retain the full charge after failure. Never allocate unreserved output. Then write/fsync staging files and their directories, validate endpoints/digests, rename the publication and new immutable run commit into final generated locations, and fsync parent directories. Only the final atomic replace of `state.json.committed_ref`, after all referenced files are durable, publishes the new graph, scope head, boundary catalogue and counters together. Release the lock after that replace.
6. Reader sessions snapshot `committed_ref` once and ignore pending/unreachable artifacts. A conflicting second publication for `(run,family,class,owner,B)` is rejected; an already committed identical digest is a no-op without another quota reservation. Catalogue pages contain at most 256 entries and have immutable generation references. Native-ID lookup has a separate per-publication index keyed by `sha256(canonical(native_kind,native_id))`, with bounded pages of matching qualified keys, so duplicate native IDs across analytical owners remain distinct and exact lookup never scans unrelated nodes.
7. Implement writer-only `recover_pending_publication`: after acquiring the run lock, inspect only the explicit pending reservation and its generated expected files. If all prepared snapshot/commit files validate, complete the final pointer transition idempotently. Otherwise mark the reservation abandoned, keep its publication slot and byte charge, and leave discovery at the previous committed ref. No recursive repair scan or deletion. An incomplete initial write can create a known run control record but cannot advertise a graph. An abandoned exclusive lock remains `lineage_writer_busy` until explicit operator intervention; readers never repair/remove it. Record bounded health codes in the run control record without modifying historical snapshot coverage.
8. Refuse symlink roots/components and traversal escapes; open generated paths without following symlinks where supported. Resolve path safety at open. Through the Task 2 read session, reserve each head/manifest/shard/page/probe read and its byte allowance before I/O; bound files before duplicate/depth-aware decode. Session-local caches are keyed by pinned digest, never moving `latest` paths. Missing pages/digests in a committed snapshot are corruption, not empty adjacency.
9. Retain prior publications and immutable catalogue generations. No GET writes, lock acquisition, on-demand export, garbage collection, quota reset, or repair. Query loading is direct indexed lookup against a committed generation. This is a rebuildable researcher read model, not authoritative simulation storage.

### Required Interfaces and Contracts
Factories `create_lineage_reader(root)` and `create_lineage_publisher(root)` return separate capabilities. Scope/run/identity-owner rules are validated against every manifest. Reader supports pinned snapshot and catalogue generations when `state.json` advances. Existing publications survive reader/process reconstruction. Artifact root is trusted local operator storage, not arbitrary downloadable archives. Capture sessions expose bounded publication receipts for the scopes actually committed at B; Task 9 uses those receipts rather than discovering scopes by a directory scan.

### Requirement Evidence
Historical navigation and bounded/paginated request; architecture's separation of subjective artifacts from replay and permission for research filesystem composition. This choice preserves SQL head `0017` and avoids adding tables just because a feature exists.

### Error Handling and Logging
`lineage_writer_busy`, `lineage_publication_conflict`, `lineage_storage_unavailable`, `lineage_snapshot_corrupt`. Never log configured roots, file paths, graph payloads or content-derived identifiers. Cancellation before rename leaves an invisible staging directory; cleanup is an explicit operator action outside this plan.

## Task 8: Capture lineage only after complete finalization

### Intent / Implementation Steps
1. Add `SimulationRunner.set_lineage_boundary_sink(sink)` before start only, separate from the existing cultural sink and generational boundary observer. The new sink is optional and absent by default; do not reuse `_publish_boundary`, whose failure changes stop evidence.
   Preflight: revalidate current `run_one_tick`, `recover_pending_finalizations`, initialization and fork restoration call sites; the former concurrent V3-38 work is now present in the clean application tree. Preserve it rather than replacing an older reconnaissance-era runner.
2. Add metadata-only `AgentRuntime.export_lineage_owner_state()` and runner extraction using existing owner checkpoints/exports, `WorldEngine.detached_objective_projection`, `WorldEngine.kinship_graph`, and the existing `_engine_snapshot` helper already used by `capture_fork_checkpoint` for artifact metadata. Strip marks/bodies into typed source records immediately; never serialize a full snapshot into the read model. Domain-specific field allowlists are the Task 3–4 projectors. A detached frame carries no engine reference and no full checkpoint serialization. Do not call `export_finalized_research_boundary` merely for lineage: it exports much broader memory/belief content and has fork-only lifecycle constraints.
3. Publish B=0 only after runtime initialization and a successful no-pending-finalizations check. Publish B=t+1 only after all subjective finalizations for committed tick t succeed. Mirror the existing cultural-capture call sites in normal execution, retry/recovery and initialization. Never capture half-finalized owner sets.
4. Await the async sink once per finalized boundary; do not introduce an unbounded task queue. The sink streams normalized projection batches and uses Task 4's deterministic current/prior merge, including stub upgrades and accurate last-observed boundaries. Apply row/encoded-byte caps during extraction/normalization, not only after building the final snapshot. Distinguish current B source completeness from uncaptured/pruned history. No peer content is copied into a live owner state.
5. Composition options select cadence (default every boundary), explicit baseline and the caps fixed in Task 2. Cadence/skipped prefix is declared in coverage; exact queries at skipped boundaries are unavailable. Stop capture on a cap or export/storage error, retain all prior publications and record a bounded health code. Never alter world commits, commands, cognitive state, run stop reasons or result bytes because capture failed. Propagate task cancellation without falsely marking a boundary published.
6. A retry of the same finalized boundary is idempotent; different data for that boundary fails capture. Restored/fork children get separate run namespaces and explicit missing-prefix/baseline metadata. They cannot borrow a parent's private graph as child history. Read artifacts cannot restore subjective runtimes.
7. Add optional `lineage_sink` to `SimulationRunner.from_fork_checkpoint`, parallel to its existing `cultural_sink` parameter. Install it on the new child before restoring `_ticks_committed`/`_started`; after all owners/control state are restored, publish B=F as the child's actual baseline. Do not use the public pre-start setter after restoration, reset ticks to evade its guard, or reuse the parent's writer/session. Child B<F is unavailable; owner state actually restored at F is valid baseline evidence. Lineage publication failure only disables lineage capture and must not follow the existing cultural fork path that raises on baseline-capture failure.
8. Implement the neutral `LineageCaptureSession` in `simulation.lineage_capture` over read/publish ports and typed options; it implements the sink, bounded merge and receipt/status access, but performs no analytical inference or concrete filesystem composition. Its receipt index identifies successfully committed scopes at each captured B; detailed mentorship metadata remains in its immutable owner publication. Trusted post-run composition pages those exact publications to obtain Task 1 records, without audit/latest-checkpoint fallback. Partial per-scope publication failures never make an incomplete run boundary look fully captured. Use Task 2's separate bounded producer read budget for prior-graph merging, not the smaller HTTP budget and not unlimited reads.

### Required Interfaces and Contracts
`LineageCaptureOptions` and `LineageCaptureStatus` are composition-only frozen types. Capture does not enable cognitive modes. Analytical institution/peer-join publications are produced separately from detached completed evidence (Task 9); the runner never imports analysis or experiments. Preserve `prepare_parallel=False`.

### Error Handling and Logging
DEBUG: boundary entered/published, scope counts, byte counts. WARN: first capture failure with stable code and B, then stop repeated attempts. No raw exceptions, ledger bodies, source content keys or graph hashes. Storage failure must not enter the generational `HISTORICAL_ARTIFACT_FAILURE` stop path.

## Phase Risks and Mitigations
- Storage growth: opt-in cadence and hard total cap; explicit health/gaps, no silent eviction.
- Historical capture after ledger pruning: preserve only previously observed records and report uncaptured ancestry as unresolved.
- Filesystem persistence mistaken for truth: separate ports, evidence classes and no live readers.
